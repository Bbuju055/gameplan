# Voice: what a person sees while a run works

Every message a run shows counts, not only its last one: the short notes while it works, the
checks and the close. The people using the suite are communications professionals, not
developers. Each command and each skill carry a one-line version of this rule
and point here.

## The rule

- **A working note is one plain line about the work, or nothing.** "Looking for reporters who
  covered oral obesity drugs in the last 90 days." A plain line on what happens next is fine
  too ("Now the client's files.", "Building the coverage report now."): clumsy, and nobody is
  misled by it. A note never names what the run uses to do the work (a tool, a command, a
  setting, the contract), and never gives a count or a result: those go with the result.
- **A question carries what it asks about.** Whatever a person must read in order to answer (a
  draft, a list, findings) is in the same message as the question, in full. A working note is
  never where it goes, and nothing worked out earlier counts as shown.
- **Nothing internal is named.** No tool, script, file, folder path, skill, plugin, setting,
  key, rule or row id, and no command the run itself uses ("reading the client-folder
  contract", "the org config exists", "using the Read tool instead"). Saying in plain words
  what is being looked at or done next is fine: "the client's folder", "your media list", "the
  calendar", "Now the client's files.". The next two points are the only exceptions.
- **What a person must act on is named.** A command they can type ("/target"), a menu path in
  the app ("Customize, then Connectors"), a connector or plugin they need to add ("That needs
  the media-targeting plugin, which isn't installed here"), and the AI engines and public
  sources a result is about (Claude, ChatGPT, SEC filings, PubMed). Nothing else from the list
  above.
- **What a result rests on is said with the result**, in the person's terms, and never in a
  working note. Three things only:
  - how much of their own material was used ("Read 412 rows, used 407, skipped 5, mostly blank
    beat fields");
  - what could not be reached, and what that means for the result;
  - what was reviewed and found fine, when the result is itself a review ("your searches look
    well-fitted").
- **A check that passed is never mentioned.** A file the run made is handed over by name, with
  nothing about its checks. Only a file that could not be made right is spoken of, once, in plain
  words: what is wrong with it and what the person should do.
- **An answer is never acknowledged in a message of its own.** No "Saved.", "Got it." or "Thanks"
  between a person's answer and the work it lets go on: what the answer changed is said once,
  with the result it belongs to.
- **Each thing is said once in a flow.** A file is named once, in the message that hands it
  over. An update shown for approval is not listed again after the approval. A plan said at the
  start is not said again at the close. Two skills in one flow never each say the same thing:
  the one that runs last says it.
- **A step that is refused is retried another way without saying so.** When it cannot be done
  at all, say once, in plain words, what could not be done and what that means for the result.
- **No internal statuses.** Not "staged", "pending review", "hand-off", "stage 3" or "draft
  row". Say what happened in the person's terms: "added to the list your media lead reviews".
- **What is saved for a person is named** by its name in Deliverables, as the client-folder
  contract says ("Saved: ..."). Storage files never are.
- No em dashes in anything a person reads: a sentence takes a comma, a colon or a full stop, and a
  title takes " - ", as file names in Deliverables do.
